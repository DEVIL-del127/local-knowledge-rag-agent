# STUDY 私人知识库 Agent 项目详细讲解

> 本文以当前代码（2026-09-08）为准，目标是让读者能够讲清楚项目解决什么问题、一次请求如何流转、PDF 如何安全入库，以及各模块为何这样设计。`docs/history/` 中的早期设计文档仅用于追溯，本文件优先采用当前正式入口和运行时代码。

## 1. 项目定位

STUDY 是一个面向私人论文/PDF 资料库的本地优先智能问答系统。它不只是“把文档塞给大模型”，而是把系统拆成五个相互约束的部分：

1. 文档入库：解析 PDF，提取结构和书目信息，切块并生成向量。
2. 双路检索：Elasticsearch 做关键词/BM25 检索，ChromaDB 做语义向量检索。
3. 语义理解：把自然语言请求编译成 RequestIR 和 LogicalPlan，并判断是否可以执行。
4. Agent 运行时：以可恢复的状态图执行检索、证据验证、回答生成和引用校验。
5. 企业级保障：代际发布、不可变清单、检查点、预算、限流、熔断、隐私、审计、记忆和遥测。

项目的核心思想可以概括为：**先把用户要求变成可验证的执行契约，再在固定的数据快照上执行，最后只允许通过证据和引用校验的回答提交。**

## 3. 两个入口与两条主链

### 3.1 正式问答入口：`agent_main.py`

正式启动命令是 `python agent_main.py`，安装后也可使用 `study`。启动过程为：

```text
读取项目根目录与 .env
  -> 配置 UTF-8 和日志
  -> AppSettings.from_env()
  -> build_application()
  -> AgentApplication.run()
  -> run_agent_loop()
```

`agent/application.py` 是依赖组合根。它负责创建检索后端、DeepSeek 客户端、预算/限流/熔断/缓存、记忆、遥测、语义编译器、检查点存储和正式运行时。业务类不自行到处创建依赖，这让测试能注入替身，也让资源关闭顺序可控。

### 3.2 入库与维护入口：`main.py`

`main.py` 中的 `PDFSearchSystem` 封装正式库/测试库、ES、向量库和 PDF 处理。当前默认入库方式是 staged generation；正式库明确禁止 legacy 原地重建。该入口也保留独立 ES、向量和混合检索菜单，便于维护和诊断。

### 3.3 正式库与测试库隔离

`PDFSearchSystem.DB_CONFIG` 为两套库分配不同 PDF 目录、输出目录、向量目录、ES 索引和 Chroma collection。这样测试建库不会覆盖正式知识库。`AGENT_DB` 只允许 `main` 或 `test`，启动阶段即拒绝错误值。

## 4. 启动阶段如何实现

### 阶段 1：环境与配置

`agent_main.py` 解析 `STUDY_PROJECT_ROOT`，加载 `.env`，再由 `AppSettings` 统一读取 ES、Ollama、模型、数据库、运行模式、注册表和 MCP 配置。标准输出被重配置为 UTF-8 且使用替换策略，目的是避免 Windows 控制台中的损坏字节使进程崩溃。

### 阶段 2：懒加载检索后端

应用使用 `LazySearchBackend` 包装 `PDFSearchSystem`。ES、Chroma 和 Ollama 的昂贵连接直到真正检索时才建立，因此通用聊天或配置检查不必先等待整个检索栈。

### 阶段 3：防护组件

- `TokenBudget`：记录会话与每日 token 消耗，状态持久化。
- `RateLimiter`：SQLite 滑动窗口限流，默认每分钟 20 次。
- `CircuitBreaker`：连续模型失败后暂时断路，避免持续冲击故障服务。
- `PersistentCache`：答案缓存带容量和 TTL，降低重复调用成本。
- `ModelCallLedger`：持久记录模型调用，支撑预算一致性和审计。

这些能力被放在模型/请求边界，而不是散落在提示词中，因为资源限制必须由确定性代码强制执行。

### 阶段 4：记忆与遥测

`MemoryManager` 启动用户会话，使用同一个 `bge-m3` 嵌入器做长期记忆向量检索。`TelemetryBus` 只记录问题侧和执行摘要，并采用有界 request_id 去重、异步 recorder 和 fail-silent 设计：日志故障不会破坏回答。

### 阶段 5：语义编译与运行时

默认 `AGENT_EXECUTION_PROFILE=enforce`。应用创建：

- 只读 `GenerationRegistry`，用于取得 ACTIVE 知识库代际；
- `ContractStore`，保存内容寻址的不可变契约；
- `SemanticCompilerAdapter`，连接当前 `kb-agent/nlu_v2` 语义引擎；
- `SQLiteCheckpointStore`，保存每个用户/会话/线程的请求状态；
- `RuntimeSemanticGraph`，执行语义理解与准入；
- `RequestExecutionGraph`，执行完整请求生命周期；
- `RuntimeAgentFacade`，维持与旧 `PrivateKnowledgeAgent` 相同的 `chat()` 接口。

运行模式有三种：`enforce` 由新运行时权威执行；`shadow` 先返回旧链结果，新运行时仅旁路观察且失败不影响用户；`off` 完全走旧 Agent，作为回滚通道。

## 5. 一次用户请求的完整生命周期

正式请求图定义在 `agent/runtime/execution_graph.py`：

```text
admit -> route
           |-> output_action -> commit
           |-> non_kb       -> commit
           |-> resume       -> bind -> retrieve -> validate_evidence
           |                              -> synthesize -> verify_citations -> commit
           `-> kb -> understand -> bind -> retrieve -> validate_evidence
                                      -> synthesize -> verify_citations -> commit
```

### 5.1 CLI 接收请求

`run_agent_loop()` 读取输入，为每轮生成 UUID `request_id`，调用 `agent.chat()`。成功后最多保留 12 轮本地对话历史；记忆写入是旁路操作，失败只记日志，不中断对话。`quit/exit/q/back/menu` 返回菜单。

### 5.2 admit：持久化准入

运行时先用用户、session、thread 和 request_id 建立请求身份，并在检查点/操作存储中申请执行权。该阶段负责重复请求、并发冲突和已提交结果的处理，防止客户端重试造成重复副作用。图中有明确的 durable admission/commit 边界。

### 5.3 route：领域和对话行为路由

`DomainRouter` 不只区分“检索/聊天”，还结合 `DialogueResolver` 识别确认、拒绝、取消、修改、澄清回答等对话动作。请求被分为：

- `output_action`：确认、取消或修改上一步输出/操作；
- `non_kb`：通用聊天或不应进入知识库的请求；
- `resume`：用户回答了上轮澄清问题，从检查点继续；
- `kb`：需要知识库语义理解和检索。

这种设计解决了多轮场景中的“是”“第二个”“改成近五年”等短句无法脱离上下文理解的问题。

### 5.4 kb / pin_generation：固定数据快照

进入知识库链后，运行时从注册表读取 ACTIVE generation，固定其 ES 物理索引、Chroma 物理集合、manifest、catalog 和摘要。后续所有检索都必须使用这份 snapshot，不能在一次请求中途漂移到刚发布的新库。

这是项目最关键的一致性设计：回答不仅与查询有关，也与“使用了哪一代数据、哪版 schema、哪套嵌入模型”绑定。

### 5.5 understand：语义编译

`RuntimeSemanticGraph` 依次执行：

```text
load_context -> pin_generation -> understand -> admission
                                       | 可执行 -> plan -> commit_compile
                                       ` 不可执行 ------> commit_compile
```

`SemanticCompilerAdapter` 将当前 catalog 转成 NLU 引擎需要的字段契约，然后生成：

- RequestIR：用户目标、实体、字段角色、条件、时间、分组、聚合、复合事件等；
- LogicalPlan：后续实际执行步骤；
- literature query：面向论文检索的规范化查询；
- decision：`execute`、`clarify`、`blocked`、`unsupported_analytics` 或 `error`；
- 各类 digest：证明使用了哪份输入、配置、源码和契约。

引擎采用“规则提供确定性骨架，受约束 LLM 只补足候选”的思路。`kb-agent/nlu_v2` 中的 clause graph、field binding、role grounding、reference binding、event closure、logical planner 等模块，把复杂请求拆成有类型、可追踪的结构。若存在缺失槽位或歧义，系统生成确定性的澄清问题，而不是猜测执行。

### 5.6 bind：绑定技能和执行快照

LogicalPlan 被绑定到已注册技能。知识库检索、诊断、管理、记忆和白名单 MCP 工具通过统一 SkillRegistry 暴露。MCP 配置限定 `allowed_tools` 与 `read_only`；配置失败时不会偷偷扩大权限。

绑定后生成 execution snapshot，记录技能名、参数、代际与逻辑计划摘要。后续恢复执行必须重新验证这份快照，防止用户澄清期间数据或工具契约已经变化。

### 5.7 retrieve：只读检索

检索网关在固定物理资源上执行计划。基础召回包括：

1. ES 路：标题、别名、关键词、摘要、正文的 BM25；标题等字段加权更高，并支持年份、语言、文档类型、document_id 过滤。
2. 向量路：查询经 Ollama `bge-m3` 转为向量，在 Chroma cosine collection 中查询。
3. 融合：旧 `hybrid_search()` 使用 Reciprocal Rank Fusion；同一文档的多个向量块只取最佳排名贡献一次，避免长文档因块多而刷高得分。

旧向量链会把命中块与前后块各最多 200 字拼接，减少固定窗口切块导致的断句。正式 staged 链则使用结构化 chunk 和显式物理 collection。

### 5.8 validate_evidence：证据门

召回结果不能直接送给模型。该节点检查结果状态、代际、文档身份、内容哈希、页码/定位信息和执行通道，并把后端不可用、空库、无匹配和执行失败区分开。区别这些状态很重要：无匹配不能伪装成系统故障，系统故障也不能回答成“资料不存在”。

### 5.9 synthesize：基于证据生成

验证通过后，运行时调用旧 Agent 中成熟的 `answer_from_observations()`/证据回答能力。提示词要求：具体文献事实必须来自证据，证据不足要明确说明，文档中的提示注入内容一律视为不可信数据，并使用 `[E1]` 等编号标注依据。

### 5.10 verify_citations：引用验证

生成回答后再次检查引用是否指向真实返回的证据、编号是否合法、必需引用是否缺失。回答生成和引用验证是两个节点，意味着“模型写出了引用”不等于“引用有效”。失败时进入受控结果而不是提交未经证明的答案。

### 5.11 commit：原子提交与旁路投影

最终 reply、意图、状态和必要操作在持久存储中提交。若请求产生记忆操作，先记为耐久事件，再投影到 `MemoryManager`；投影失败可在后续请求恢复，不能因重试再次执行整个请求。提交后 `RuntimeAgentFacade` 发出一次遥测事件。

## 6. PDF 入库的完整生命周期

### 6.1 为什么不原地重建

早期流程会删除/清空当前 ES 和 Chroma 后重建。如果解析到一半失败，线上库就可能处于不完整状态。当前方案使用 generation：先构建全新的物理索引和集合，验证完毕后再原子切换 ACTIVE 指针；旧代际保留，可回滚。

### 6.2 stage：创建代际

`IngestionCoordinator.stage()` 创建 generation id 和构建日志，并为该代际分配独立 ES 索引、Chroma collection、manifest。注册表用 SQLite 保存状态与 revision，支持并发比较交换。

### 6.3 parse：Docling 解析和缓存

正式 staged 流程使用 `DoclingParser`，输出 Markdown、页面块和 parser version，并按源文件哈希缓存解析结果，避免重复处理昂贵 PDF。Docling 不可用时在开始昂贵工作前失败，ACTIVE 库不受影响。

旧兼容解析器 `PDFParser` 的策略是：先 MIME 校验；pdfplumber 分页提取；页面有效文本不足 50 字时用 300 DPI Tesseract OCR；整体失败再用 PyPDF2；最后统一空白与字符。它适合解释项目演进，但不是当前正式 staged 解析主路径。

### 6.4 metadata：书目信息提取

系统从文件名、Markdown 标题和前置信息推断标题、年份、语言、文档类型、主题别名。年份按 Elsevier PII、明确文件名、arXiv、前置信息依次取可信来源；文档类型区分期刊、会议、预印本、学位论文和普通论文。代码还专门处理 `ESN` 缩写碰撞，避免把其他领域同名缩写误标成 Echo State Network。

### 6.5 chunk：结构化切块

staged 链使用 `ingestion/chunking/structural.py`，以文档结构和最大字符约束生成块；每块携带 document_id、content_hash、generation、chunk_index 和页码范围。旧链为 500 字固定窗口、100 字重叠。结构化切块更利于引用定位，固定窗口则简单且适合兼容回退。

### 6.6 双写 staging 后端

- ES staging sink 写全文、标题、书目元数据与代际字段；
- Chroma staging sink 写块文本、元数据和 `bge-m3` 向量；
- embedding dimension 固定为 1024，并在准备和激活时校验。

双写完成并不等于可以发布。系统会比较 ES 文档集合、向量文档集合、预期 chunk 集合和实际向量记录，任何不一致都会拒绝该代际。

### 6.7 manifest：不可变发布证据

manifest 记录：源文件哈希、接受/隔离状态、解析器、切块器、嵌入模型、ES cluster/index UUID、mapping/settings digest、Chroma collection id、catalog digest、文档/块集合 digest 和计数。它以内容哈希为地址写入，注册表保存 locator、digest、长度和 schema version。

内容寻址的意义是：只要文件被改一个字节，digest 就变；激活阶段可证明所审查的 manifest 正是当前要发布的那份。

### 6.8 quality gate 与 PREPARED

解析为空、质量不合格或契约不一致的文档被 quarantine；代际只有在文档数、块数、维度、物理身份和集合摘要全部一致后才进入 PREPARED。此时不会自动上线，日志明确要求先审查 manifest，再显式激活。

### 6.9 activate：原子切换

`activate_generation()` 重新读取并验证内容寻址 manifest，再现场检查 ES/Chroma 物理身份、文档集合和向量维度。最后通过 expected active generation、registry revision 和 record revision 做 compare-and-swap 切换。并发发布或审查后发生变化会导致激活失败，而不是覆盖另一位操作者的结果。

PREPARED 代际激活后成为 ACTIVE，原 ACTIVE 退役；RETIRED 代际也可通过同一套验证回滚。

## 7. 记忆系统设计

记忆不是把全部历史无限塞进上下文，而是分层管理：

- L1 会话：当前轮次、任务步骤和短期上下文；
- L2 长期事实：偏好、任务、约束和事实，可关键词/向量召回；
- L3 用户画像：按置信度和时间合并的稳定信息。

每轮在回答成功后调用 `ingest_message()`。写入前执行字符、格式、口语、否定范围、代词、PII 等清洗，并做保真检查、字面去重和锚点冲突识别。只有允许的意图进入记忆；LLM 提取失败时存在受控 fallback。

会话结束时生成摘要、提升长期事实、更新画像并向量化。记忆数据库内容通过加密 envelope 保存，并用 AAD 绑定用户、session 和 revision，防止密文被跨身份替换。outbox 使数据库事实提交和向量投影可以最终一致地恢复。

## 8. 状态、可靠性与安全设计

### 8.1 检查点与恢复

`SQLiteCheckpointStore` 以 `(user_id, session_id, thread_id)` 为键保存 `AgentState`，revision 实现乐观并发控制。澄清后不是重新猜整条请求，而是载入上轮语义结果和固定快照，验证后从 resume 重新接入 bind。

### 8.2 无隐式重试副作用

请求图没有给模型/工具节点安装自动 retry。CLI 也先检查 `chat()` 签名再传 request_id，不会捕获 TypeError 后再次调用而重复副作用。能安全重做的纯节点、预算模型节点和幂等提交节点在语义图中被显式标记。

### 8.3 隐私边界

检索到的文档被视为不可信输入；系统提示明确禁止执行文档中的指令。遥测默认只采集问题侧和摘要字段。状态有 privacy envelope、OS secret protection、受保护备份和迁移权限相关实现及测试。

### 8.4 失败隔离

- 向量检索失败时，旧混合链可降级为纯 ES；
- 日志/记忆旁路失败不影响已生成回答；
- shadow 运行时失败不影响 legacy 回答；
- enforce 下关键契约、代际或记忆投影未恢复时 fail closed；
- 应用使用 `ExitStack` 注册资源回收，并保留原始初始化异常。

## 10. 关键数据结构

- `IntentPrediction`：意图、是否检索、置信度、用户目标、路由来源和原因。
- `AgentReply`：回答、意图、证据、技能调用及执行信息，是 CLI 与运行时的兼容边界。
- `RetrievedEvidence`：来源、页码、通道、分数、片段，并生成引用标签。
- `SemanticCompileResult`：语义决策、IR、LogicalPlan、澄清问题和摘要。
- `AgentState`：跨轮请求状态、固定快照、语义结果、绑定技能、观测、错误和 revision。
- `SearchOutcome`：区分 matched/no-match/empty/provider unavailable/failed，而不只返回空 list。
- `GenerationRecord`：代际状态、物理资源、manifest 引用、契约摘要和 revision。
- `IngestionManifest`：可审查、可验证的完整发布证据。

## 11. 重要设计取舍

### ES + Chroma，而不是只用一种检索

BM25 擅长精确术语、标题、缩写和可解释过滤；向量检索擅长措辞不同但语义相近的内容。RRF 用排名而非原始分数融合，避免 ES 分数和 cosine 相似度量纲不一致。代价是部署组件更多，双写与一致性验证更复杂。

### LangGraph，而不是一个巨大的 `chat()`

图把准入、理解、检索、校验和提交拆成有名字的状态节点，便于恢复、测试和审计。代价是状态模型、条件边和检查点代码明显增加。

### 契约优先，而不是完全交给 LLM 决定

LLM 对自然语言有弹性，但不适合独自保证字段存在、时间范围合法、复合事件闭合或工具参数安全。因此项目用类型、catalog、规则和 validator 划定边界，只让模型在有限候选中补足。代价是 NLU 模块数量多，新分析能力需要扩展契约。

### staged generation，而不是原地更新

新库先准备、验证、人工批准，再原子切换，获得可回滚和可追溯性。代价是同时保留多份索引/向量集合，占用更多磁盘且需要垃圾回收策略。

### fail closed 与 fail silent 的边界

会影响事实正确性和副作用一致性的组件（代际、证据、契约、提交）失败时关闭执行；仅辅助观测的组件（日志、部分记忆投影）失败时隔离。这个边界比“所有异常都吞掉”或“任何旁路异常都阻断”更符合系统风险。

## 14. 当前边界和改进方向

以下是根据代码做出的工程判断，不是已经实现的事实：

1. `main.py` 仍同时承担维护 UI、legacy 入库和检索 facade，后续可拆成 `ingest`、`search`、`admin` 三个 CLI。
2. staged 与 legacy 的切块/解析逻辑并存，长期应明确 legacy 的退役时间，减少双语义维护成本。
3. 项目依赖 ES、Ollama、Chroma、DeepSeek 和可选 Docling，部署诊断虽已有状态模型，但仍适合提供统一 health 命令。
4. 多代际会持续占用物理资源，需要审计后、可恢复的垃圾回收流程；不能简单删除非 ACTIVE 资源，因为 RETIRED 代际承担回滚作用。
5. 当前主要界面是 CLI。若开放 FastAPI，必须复用 request_id、身份、准入和提交边界，不能绕过运行时直接调用检索或模型。
6. 仓库当前存在大量未提交修改和生成的验收材料，制作发布版本前应先区分源码、测试证据、运行产物与历史档案。

## 16. 面试式复述

### 30 秒版本

这是一个本地优先的私人论文知识库 Agent。PDF 经过 Docling 解析和结构化切块，同时写入 Elasticsearch 与 Chroma；查询先编译成 RequestIR 和 LogicalPlan，再在固定的 ACTIVE 数据代际上执行混合检索，证据验证后由 DeepSeek 生成答案并校验引用。系统还用 LangGraph、SQLite 检查点、内容寻址 manifest、预算/限流/熔断和分层记忆保证可恢复性与可靠性。

### 1 分钟版本

项目解决的重点不是普通 RAG 的“能搜到”，而是“这次回答用了哪一代数据、执行了什么计划、证据是否有效、失败后能否恢复”。入库采用 staged generation：新 ES 索引和 Chroma collection 构建完成后，通过文档集、块集、embedding dimension、物理资源和 manifest digest 校验，再显式原子激活。问答端使用两层 LangGraph：语义图把自然语言转成 IR/计划并决定执行或澄清；请求图负责准入、路由、固定代际、技能绑定、检索、证据校验、生成、引用验证和提交。BM25 与向量召回通过 RRF 融合，所有具体文献结论必须绑定证据。

### 最值得讲的难点

最值得讲的是“跨轮澄清时保持执行一致性”：用户补充条件前后，知识库可能刚好发布新代际。项目将 generation snapshot、IR、LogicalPlan 和 skill bindings 做摘要并持久化；恢复时重新校验快照，再从 bind 节点继续，因此不会把旧问题结构和新数据契约混在同一次执行里。
